LLM-as-Judge — Évaluer une réponse ouverte avec un autre LLM

Programme7 jours3-4h/jour

Définition

Le LLM-as-judge est un patron d'évaluation dans lequel un LLM (le juge) note la sortie d'un autre LLM (l'agent évalué) selon des critères définis. Il remplace l'annotation humaine quand la tâche est ouverte — génération de texte, résumé, conversation, raisonnement — là où une comparaison exacte avec une ground truth est impossible.

:::situation Thales, équipe IA interne — Agent de rédaction de synthèses techniques

L'agent produit des synthèses de rapports d'incidents systèmes. Les synthèses sont jugées "bonnes" ou "mauvaises" par les ingénieurs, mais annoter 500 sorties par semaine à la main est impossible. Problème : comment savoir si le prompt v2 est meilleur que le prompt v1 sans annoter manuellement ? Solution : un LLM juge les deux sorties en aveugle et donne un score + une justification. :::

Le problème : les tâches ouvertes résistent aux métriques classiques

:::problem Avant — on mesure ce qui est facile, pas ce qui compte

# Tentation : utiliser des métriques NLP classiques
from rouge_score import rouge_scorer
scorer = rouge_scorer.RougeScorer(["rougeL"])
score = scorer.score(reference, prediction)
# score.rougeL.fmeasure → 0.43

# Le problème : ROUGE mesure la similarité lexicale
# "Le serveur est tombé à 14h" et "La panne a démarré à 14h00"
# → ROUGE score faible, mais les deux phrases disent la même chose
# → Un agent qui paraphrase parfaitement sera pénalisé

BLEU, ROUGE et METEOR comparent les mots, pas le sens. Pour une tâche où la formulation peut varier librement, ils sont quasi inutiles. :::

Comment ça marche — les trois formes de LLM-as-judge

Forme 1 — Score absolu (scoring)

Le juge note la réponse sur une échelle de 1 à 5 selon un critère précis.

import anthropic

client = anthropic.Anthropic()

JUDGE_PROMPT = """Tu es un évaluateur expert. Évalue la réponse suivante selon le critère FIDÉLITÉ FACTUELLE.

CRITÈRE — Fidélité factuelle :
Score 5 : toutes les affirmations sont vérifiables et correctes
Score 4 : une imprécision mineure, rien d'incorrect
Score 3 : une erreur factuelle non critique
Score 2 : plusieurs erreurs factuelles
Score 1 : majoritairement incorrect

CONTEXTE SOURCE :
{context}

RÉPONSE À ÉVALUER :
{response}

Réponds uniquement avec ce JSON :
{{"score": <entier 1-5>, "justification": "<une phrase>"}}"""

def judge_factuality(context: str, response: str) -> dict:
    result = client.messages.create(
        model="claude-opus-5",  # utiliser le modèle le plus capable comme juge
        max_tokens=200,
        messages=[{
            "role": "user",
            "content": JUDGE_PROMPT.format(context=context, response=response)
        }]
    )
    import json
    return json.loads(result.content[0].text)

score = judge_factuality(
    context="Le serveur A est tombé le 12/03 à 14h22 suite à une saturation mémoire.",
    response="Le serveur A a rencontré une panne mémoire vers 14h20 le 12 mars."
)
# → {"score": 4, "justification": "Légère imprécision sur l'heure (14h20 vs 14h22), le reste est correct."}

Forme 2 — Comparaison par paire (pairwise)

Le juge compare deux réponses et désigne la meilleure. Plus fiable que le score absolu car il élimine la variance d'échelle.

PAIRWISE_PROMPT = """Compare ces deux réponses à la même question. Désigne laquelle est meilleure.

QUESTION : {question}

RÉPONSE A : {response_a}

RÉPONSE B : {response_b}

CRITÈRES (par ordre d'importance) :
1. Exactitude factuelle
2. Clarté pour un ingénieur non-expert
3. Concision

Réponds uniquement avec ce JSON :
{{"winner": "A" | "B" | "tie", "reason": "<une phrase>"}}"""

def compare_responses(question: str, response_a: str, response_b: str) -> dict:
    result = client.messages.create(
        model="claude-opus-5",
        max_tokens=200,
        messages=[{
            "role": "user",
            "content": PAIRWISE_PROMPT.format(
                question=question,
                response_a=response_a,
                response_b=response_b
            )
        }]
    )
    import json
    return json.loads(result.content[0].text)

:::callout-insight Pourquoi pairwise est plus fiable que scoring

Demander "note cette réponse de 1 à 5" dépend de l'interprétation de l'échelle. Demander "laquelle est meilleure entre A et B" est une comparaison relative — le LLM juge un rapport, pas une valeur absolue. C'est aussi plus cohérent avec ce qu'on veut vraiment savoir : "est-ce que le prompt v2 est meilleur que v1 ?" :::

Forme 3 — Checklist décomposée (G-Eval)

Le pattern G-Eval décompose le critère en sous-questions binaires, puis agrège. Réduit la variance et donne une justification structurée.

GEVAL_COHERENCE = """Évalue la COHÉRENCE de ce résumé par rapport au document source.

DOCUMENT SOURCE :
{document}

RÉSUMÉ :
{summary}

Réponds à chaque question par oui ou non :
1. Le résumé ne contient-il aucune affirmation absente du document source ?
2. Le résumé ne contredit-il aucun fait du document ?
3. Les relations causales sont-elles correctement préservées ?
4. Les dates et chiffres cités sont-ils exacts ?

Réponds avec ce JSON :
{{"answers": [true|false, true|false, true|false, true|false], "score": <moyenne sur 4>}}"""

Les biais du juge — ce que tout le monde oublie

:::warning Trois biais documentés qui faussent les résultats

1. Biais de position : quand on compare A vs B, le LLM favorise systématiquement la réponse en première position. Correction : inverser l'ordre sur la moitié des évaluations et agréger.

2. Biais de verbosité : les LLM tendent à préférer les réponses plus longues, indépendamment de leur qualité. Correction : inclure "la concision est une qualité, ne favorise pas la longueur" dans le prompt.

3. Auto-favoritisme : Claude préférera les réponses générées par Claude, GPT-4 préférera celles de GPT-4. Correction : utiliser un modèle différent comme juge, ou comparer les résultats entre juges. :::

def robust_pairwise(question, response_a, response_b, n_trials=4):
    """
    Compare A vs B et B vs A, répète n_trials fois, agrège.
    Corrige le biais de position.
    """
    votes = {"A": 0, "B": 0, "tie": 0}

    for i in range(n_trials // 2):
        # A en premier
        r1 = compare_responses(question, response_a, response_b)
        votes[r1["winner"]] += 1

        # B en premier (inverser)
        r2 = compare_responses(question, response_b, response_a)
        # Ré-inverser le résultat
        inverted = {"A": "B", "B": "A", "tie": "tie"}[r2["winner"]]
        votes[inverted] += 1

    return max(votes, key=votes.get), votes

Calibration du juge — valider avant de faire confiance

Avant d'utiliser un LLM-as-judge en production, il faut vérifier que ses jugements corrèlent avec les jugements humains.

# 1. Annoter ~50 cas manuellement (ground truth humaine)
human_labels = [5, 4, 3, 5, 2, ...]  # scores humains

# 2. Faire noter les mêmes cas par le juge LLM
llm_scores = [judge_factuality(ctx, resp)["score"] for ctx, resp in test_cases]

# 3. Mesurer la corrélation (Spearman, plus robuste que Pearson pour des rangs)
from scipy.stats import spearmanr
correlation, p_value = spearmanr(human_labels, llm_scores)
print(f"Corrélation Spearman : {correlation:.2f} (p={p_value:.3f})")

# Seuil acceptable : ρ > 0.7
# En dessous : le critère est mal défini ou le juge n'est pas fiable sur ce critère

Quand utiliser le LLM-as-judge

  • Tâches ouvertes : résumé, génération de texte, conversation, raisonnement
  • Comparaison de versions (prompt A vs prompt B)
  • Quand l'annotation humaine est trop coûteuse à grande échelle
  • En complément des métriques de tâche classiques, jamais en remplacement si les métriques exactes sont disponibles

Quand ne pas l'utiliser seul

  • Quand la tâche est exacte et vérifiable (extraction de données structurées, calcul, classification) — une métrique de tâche directe est plus fiable et moins coûteuse
  • Quand le modèle juge a une fenêtre de contexte insuffisante pour lire le document source en entier
  • Sans calibration préalable sur des annotations humaines — les scores sont arbitraires sans validation

Métriques de tâche — Définir ce que "réussir" veut dire pour un agent

Programme7 jours3-4h/jour

Définition

Une métrique de tâche est une mesure quantitative qui indique si un agent a accompli ce qu'on lui demandait — pas si sa réponse semble bien, mais si elle est correcte selon un critère objectif et vérifiable.

La distinction est fondamentale : une réponse peut paraître fluide, polie, bien formulée, et être complètement fausse sur le fond. Sans métrique de tâche, on mesure la forme, pas le résultat.

:::callout-insight Essentiels : - Une métrique de tâche mesure le résultat, pas la fluidité de la réponse. - Sans critère objectif préalable, toute évaluation reste une opinion. :::

:::situation Capgemini, 2024 — Agent de traitement de contrats

L'équipe déploie un agent qui extrait les clauses de résiliation de contrats clients et les classe (résiliation unilatérale, résiliation pour faute, résiliation amiable). En démo, l'agent répond avec assurance. En production, les juristes remontent des erreurs de classification tous les jours. Le problème : l'évaluation avait été faite "à l'œil" — un ingénieur lisait 20 sorties et les trouvait cohérentes. Il n'y avait pas de métrique de tâche définie. :::

:::callout-insight Essentiels : - Une évaluation "à l'œil" sur 20 exemples ne détecte pas les erreurs systématiques en production. - La confiance perçue en démo n'est pas un proxy de la fiabilité réelle. :::

Le problème : évaluer sans critère c'est ne pas évaluer

:::problem Avant — évaluation subjective

# Ce qu'on faisait (et ce que tout le monde fait au début)
responses = agent.run(test_contracts)
for r in responses:
    print(r)  # on lit, ça "semble bien"

# Résultat : 0 % de confiance sur le comportement en production
# On ne sait pas ce qu'on ne sait pas

Le problème n'est pas la mauvaise volonté — c'est l'absence de ground truth (vérité terrain) et de critère de succès explicite. Sans ça, impossible de : - Comparer deux versions de l'agent - Détecter une régression après une modification du prompt - Savoir si le modèle sous-jacent a changé de comportement :::

:::callout-insight Essentiels : - L'absence de ground truth rend impossible la comparaison entre deux versions. - On ne peut détecter une régression que si on a une baseline mesurée au préalable. - "Ça semble bien" = 0 % de confiance pour prendre une décision de déploiement. :::

Les trois familles de métriques de tâche

:::callout-insight Essentiels : - Trois familles complémentaires : résultat final, processus/actions, contraintes opérationnelles. - Résultat final seul ne suffit pas : un agent peut être juste mais trop lent ou trop coûteux. - Chaque famille répond à une question différente : "quoi", "comment", "à quel coût". :::

Comment ça marche — construire ses métriques de tâche

Étape 1 — Construire un dataset de test avec ground truth

La ground truth (vérité terrain) est la réponse correcte connue à l'avance, annotée par un humain ou générée à partir de données réelles.

# dataset de test : liste de cas avec la réponse attendue
TEST_CASES = [
    {
        "input": "Extrait la clause de résiliation de ce contrat : [...texte...]",
        "expected_category": "résiliation_unilatérale",
        "expected_délai_préavis_jours": 30,
    },
    {
        "input": "Extrait la clause de résiliation de ce contrat : [...texte...]",
        "expected_category": "résiliation_pour_faute",
        "expected_délai_préavis_jours": 0,
    },
    # ... minimum 50-100 cas pour avoir des résultats fiables
]

:::callout-insight Pourquoi au moins 50 cas ?

Avec 20 cas, un écart de 1 erreur représente 5 points de pourcentage. Vos métriques ont une variance trop haute pour être fiables. Avec 100 cas, 1 erreur = 1 point. C'est le seuil minimal pour détecter une régression entre deux versions. :::

Étape 2 — Définir la fonction de succès

Pour chaque tâche, la question à poser : qu'est-ce qu'une réponse correcte, formalisable en code ?

def is_correct(agent_output: dict, expected: dict) -> bool:
    """
    Succès = catégorie correcte ET délai dans ±2 jours.
    Partial credit non géré ici — on commence par du binaire.
    """
    category_ok = agent_output["category"] == expected["expected_category"]
    delay_ok = abs(
        agent_output["délai_préavis_jours"] - expected["expected_délai_préavis_jours"]
    ) <= 2
    return category_ok and delay_ok

:::warning Le piège du critère trop strict ou trop lâche

Trop strict : agent_output["text"] == expected["text"] — une virgule différente = échec. L'agent peut être juste sur le fond et échouer à 100%.

Trop lâche : any(word in agent_output for word in expected_keywords) — l'agent peut mentionner le bon mot par hasard sans avoir compris.

La bonne pratique : définir d'abord ce qui compte métier (ici : catégorie + délai), pas ce qui est facile à mesurer. :::

Étape 3 — La boucle d'évaluation complète

import time
from dataclasses import dataclass, field
from typing import List

@dataclass
class EvalResult:
    total: int = 0
    correct: int = 0
    latencies_ms: List[float] = field(default_factory=list)
    errors: List[dict] = field(default_factory=list)

    @property
    def accuracy(self) -> float:
        return self.correct / self.total if self.total > 0 else 0.0

    @property
    def p50_ms(self) -> float:
        s = sorted(self.latencies_ms)
        return s[len(s) // 2] if s else 0.0

    @property
    def p95_ms(self) -> float:
        s = sorted(self.latencies_ms)
        return s[int(len(s) * 0.95)] if s else 0.0


def run_eval(agent, test_cases: list) -> EvalResult:
    result = EvalResult(total=len(test_cases))

    for case in test_cases:
        t0 = time.perf_counter()
        try:
            output = agent.run(case["input"])
            latency_ms = (time.perf_counter() - t0) * 1000
            result.latencies_ms.append(latency_ms)

            if is_correct(output, case):
                result.correct += 1
            else:
                result.errors.append({
                    "input": case["input"][:80],
                    "expected": case["expected_category"],
                    "got": output.get("category"),
                })
        except Exception as e:
            result.errors.append({"input": case["input"][:80], "error": str(e)})

    return result


# Utilisation
result = run_eval(my_agent, TEST_CASES)
print(f"Accuracy : {result.accuracy:.1%}")
print(f"Latence p50 : {result.p50_ms:.0f} ms | p95 : {result.p95_ms:.0f} ms")
print(f"Erreurs : {len(result.errors)}/{result.total}")

Étape 4 — Suivre l'évolution dans le temps

Une métrique prise une fois n'a aucune valeur. La valeur vient de la comparaison entre versions.

import json
from datetime import datetime

def save_eval(result: EvalResult, version: str, filepath: str = "eval_history.jsonl"):
    record = {
        "timestamp": datetime.utcnow().isoformat(),
        "version": version,
        "accuracy": result.accuracy,
        "p50_ms": result.p50_ms,
        "p95_ms": result.p95_ms,
        "n_errors": len(result.errors),
        "n_total": result.total,
    }
    with open(filepath, "a") as f:
        f.write(json.dumps(record) + "\n")

# Après chaque modification du prompt ou du modèle :
save_eval(result, version="v1.2-prompt-refacto")

# Détecter une régression : si accuracy baisse de plus de 3 points → bloquer le déploiement
def check_regression(current: EvalResult, baseline_accuracy: float, threshold: float = 0.03) -> bool:
    regression = baseline_accuracy - current.accuracy
    if regression > threshold:
        print(f"⚠ Régression détectée : {regression:.1%} de dégradation")
        return True
    return False

:::callout-insight Essentiels : - Dataset ≥ 50 cas : seuil minimal pour que les métriques aient une variance acceptable. - La fonction de succès doit formaliser ce qui compte métier, pas ce qui est pratique à coder. - Sauvegarder les métriques à chaque version est la condition pour détecter une régression. :::

Cas réel complet — Agent de qualification de leads (BNP Paribas Leasing)

:::situation Contexte : un agent reçoit des fiches de prospects entrants (secteur d'activité, taille, CA déclaré, besoin exprimé) et doit les qualifier en trois catégories — chaud, tiède, froid — pour prioriser les appels commerciaux.

Enjeu métier : un faux négatif (prospect chaud classé froid) = opportunité perdue. Un faux positif (prospect froid classé chaud) = temps commercial gaspillé. Les deux erreurs n'ont pas le même coût. :::

# Ici la métrique de tâche doit refléter l'asymétrie des coûts
# Manquer un prospect chaud coûte 5x plus que appeler un froid inutilement

COST_MATRIX = {
    # (réel, prédit) : coût
    ("chaud", "froid"):  5.0,   # faux négatif : très coûteux
    ("chaud", "tiède"):  2.0,   # faux négatif partiel
    ("tiède", "chaud"):  0.5,   # faux positif léger
    ("froid", "chaud"):  1.0,   # faux positif : temps gaspillé
    ("chaud", "chaud"):  0.0,   # correct
    ("tiède", "tiède"):  0.0,
    ("froid", "froid"):  0.0,
}

def weighted_cost(predictions: list, ground_truth: list) -> float:
    total_cost = 0.0
    for pred, true in zip(predictions, ground_truth):
        total_cost += COST_MATRIX.get((true, pred), 0.0)
    return total_cost / len(predictions)

# Résultat : on optimise le coût pondéré, pas l'accuracy brute
# Un modèle à 85% accuracy mais qui rate tous les prospects chauds
# sera battu par un modèle à 78% qui ne rate aucun chaud.

:::callout-insight L'accuracy n'est presque jamais la bonne métrique

Pour un agent de qualification leads où 5 % sont "chauds" : un agent qui répond "froid" à tout le monde a 95 % d'accuracy. C'est le problème des classes déséquilibrées. La métrique juste ici est le recall sur les "chauds" (combien de prospects chauds on capture) ou le coût pondéré comme ci-dessus. :::

:::callout-insight Essentiels : - Quand les erreurs ont des coûts asymétriques, une matrice de coût remplace l'accuracy. - Optimiser l'accuracy sur classes déséquilibrées peut produire un agent inutile mais bien noté. :::

Quand utiliser des métriques de tâche

  • Dès qu'on a un agent en production ou en approche de production
  • Avant de modifier un prompt, un modèle ou une configuration
  • Pour comparer deux agents sur le même problème
  • Comme condition de déploiement : "ne passe en prod que si accuracy ≥ seuil X"

Quand ne pas s'y fier seul

  • Quand la tâche est ouverte (génération créative, conversation libre) — les métriques de tâche binaires ne s'appliquent pas, il faut un LLM-as-judge
  • Quand le dataset de test n'est pas représentatif de la vraie distribution de production
  • Quand la ground truth a été annotée par une seule personne — l'accord inter-annotateurs doit être vérifié (kappa de Cohen > 0.7 est le seuil usuel)

:::callout-insight Essentiels : - Définir les métriques avant la mise en production, pas après les premières erreurs de prod. - Sur des tâches ouvertes ou créatives, les métriques binaires sont insuffisantes : utiliser LLM-as-judge. - Une ground truth annotée par une seule personne est une source de biais non quantifiable. :::

Voir la réponse
Réponse

Une mesure quantitative qui indique si un agent a accompli sa tâche selon un critère objectif — pas si sa réponse semble bien, mais si elle est correcte sur le fond.

Pourquoi un dataset de test a-t-il besoin d'au moins 50-100 cas ?

Voir la réponse
Réponse

Avec 20 cas, 1 erreur = 5 points de variance. Les métriques sont trop instables pour détecter une régression. Avec 100 cas, 1 erreur = 1 point — seuil minimal pour comparer deux versions.

Qu'est-ce que la ground truth ?

Voir la réponse
Réponse

La réponse correcte connue à l'avance, annotée par un humain ou issue de données réelles vérifiées. Sans ground truth, on ne peut pas calculer de métrique de tâche.

Pourquoi l'accuracy n'est-elle presque jamais la bonne métrique ?

Voir la réponse
Réponse

Sur des classes déséquilibrées, un agent qui répond toujours "non" peut avoir 95 % d'accuracy si 95 % des cas sont négatifs. Il faut des métriques adaptées à l'enjeu métier : recall, F1, ou coût pondéré.

Voir la réponse
Réponse

Une dégradation de performance entre deux versions — détectée en comparant les métriques avant/après modification. Exemple : l'accuracy passe de 87 % à 83 % après un changement de prompt.

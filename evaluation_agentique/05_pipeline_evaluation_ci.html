Pipeline d'évaluation en CI/CD — Intégrer l'évaluation dans le déploiement

Programme7 jours3-4h/jour

Définition

Un pipeline d'évaluation en CI/CD est une suite de tests automatisés qui s'exécutent à chaque modification du système (prompt, modèle, code de l'agent) et bloquent le déploiement si les métriques chutent en dessous d'un seuil défini. C'est l'équivalent des tests unitaires pour les systèmes ML classiques, appliqué aux agents LLM.

:::situation Capgemini, mission assurance — Agent d'analyse de sinistres

L'équipe modifie le prompt système pour améliorer la concision des réponses. En développement, les réponses semblent meilleures. En production, les juristes constatent que l'agent omet maintenant certaines clauses importantes dans ses analyses. Problème : il n'y avait pas de test automatisé sur "présence des clauses critiques". Une modification de prompt est passée en prod sans garde-fou. Avec un pipeline d'évaluation en CI, ce cas aurait été bloqué avant le merge. :::

Architecture d'un pipeline d'évaluation

git push / PR ↓ [CI déclenché] ↓ ┌─────────────────────────────────┐ │ 1. Tests unitaires rapides │ < 2 min — DeepEval sur 20 cas │ (smoke tests) │ Vérifie : pas de régression majeure └─────────────────────────────────┘ ↓ (si OK) ┌─────────────────────────────────┐ │ 2. Évaluation complète │ 5-15 min — Ragas ou DeepEval complet │ (full eval suite) │ Métriques : accuracy, faithfulness... └─────────────────────────────────┘ ↓ (si OK) ┌─────────────────────────────────┐ │ 3. Comparaison baseline │ Comparer vs version précédente │ (regression check) │ Bloquer si dégradation > seuil └─────────────────────────────────┘ ↓ (si OK) [Merge autorisé / Déploiement]

Implémentation — Structure de projet

my_agent/ ├── agent.py ← code de l'agent ├── prompts/ │ └── system_prompt.txt ← prompt versionné ├── evals/ │ ├── test_agent_smoke.py ← tests rapides (DeepEval) │ ├── test_agent_full.py ← évaluation complète │ ├── baseline.json ← métriques de la version précédente │ └── testset.csv ← dataset de test versionné └── .github/workflows/ └── eval.yml ← CI GitHub Actions

Les tests smoke — vérification rapide en 2 minutes

# evals/test_agent_smoke.py
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric, HallucinationMetric
from my_agent import agent

# 5-10 cas critiques — les plus importants du domaine
CRITICAL_CASES = [
    {
        "input": "Quelles pièces justificatives pour une déclaration de sinistre ?",
        "context": ["Pour déclarer un sinistre : facture d'achat, photos des dommages, "
                   "constat si tiers impliqué, numéro de contrat."],
        "must_contain": ["facture", "photos", "constat"]
    },
    {
        "input": "Quel est le délai de remboursement ?",
        "context": ["Délai légal de remboursement : 30 jours à compter de la réception du dossier complet."],
        "must_contain": ["30 jours"]
    },
]

@pytest.mark.parametrize("case", CRITICAL_CASES)
def test_smoke(case):
    response = agent.run(case["input"], context=case["context"])

    test_case = LLMTestCase(
        input=case["input"],
        actual_output=response,
        context=case["context"]
    )

    # Vérification 1 : pas d'hallucination
    assert_test(test_case, [HallucinationMetric(threshold=0.2)])

    # Vérification 2 : les éléments critiques sont présents
    for term in case["must_contain"]:
        assert term.lower() in response.lower(), \
            f"Terme critique absent de la réponse : '{term}'"

L'évaluation complète — comparaison avec la baseline

# evals/test_agent_full.py
import json
import os
import pytest
import pandas as pd
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision
from datasets import Dataset
from my_agent import agent

BASELINE_PATH = "evals/baseline.json"
TESTSET_PATH = "evals/testset.csv"

# Seuils de non-régression : si une métrique baisse de plus de X points, bloquer
REGRESSION_THRESHOLDS = {
    "faithfulness": 0.05,      # tolérance 5 points
    "answer_relevancy": 0.05,
    "context_precision": 0.08,
}

# Seuils absolus minimaux : ne jamais descendre en dessous
ABSOLUTE_MINIMUMS = {
    "faithfulness": 0.75,
    "answer_relevancy": 0.70,
    "context_precision": 0.65,
}


def run_full_eval():
    df = pd.read_csv(TESTSET_PATH)

    data = {
        "question": df["question"].tolist(),
        "answer": [agent.run(q) for q in df["question"]],
        "contexts": [eval(c) for c in df["contexts"]],  # contexts stockés comme liste sérialisée
    }
    if "ground_truth" in df.columns:
        data["ground_truth"] = df["ground_truth"].tolist()

    result = evaluate(
        Dataset.from_dict(data),
        metrics=[faithfulness, answer_relevancy, context_precision]
    )
    return dict(result)


def test_no_regression():
    current = run_full_eval()

    # Vérifier les minimums absolus
    for metric, minimum in ABSOLUTE_MINIMUMS.items():
        if metric in current:
            assert current[metric] >= minimum, \
                f"{metric} = {current[metric]:.3f} < minimum absolu {minimum}"

    # Vérifier la non-régression vs baseline
    if os.path.exists(BASELINE_PATH):
        with open(BASELINE_PATH) as f:
            baseline = json.load(f)

        for metric, threshold in REGRESSION_THRESHOLDS.items():
            if metric in current and metric in baseline:
                drop = baseline[metric] - current[metric]
                assert drop <= threshold, (
                    f"Régression détectée sur {metric} : "
                    f"{baseline[metric]:.3f} → {current[metric]:.3f} "
                    f"(chute de {drop:.3f}, seuil = {threshold})"
                )

    # Mettre à jour la baseline si tous les tests passent
    # (seulement en CI sur la branche main)
    if os.getenv("CI") and os.getenv("GITHUB_REF") == "refs/heads/main":
        with open(BASELINE_PATH, "w") as f:
            json.dump(current, f, indent=2)
        print(f"Baseline mise à jour : {current}")

Configuration GitHub Actions

# .github/workflows/eval.yml
name: Agent Evaluation

on:
  pull_request:
    branches: [main]
    paths:
      - "agent.py"
      - "prompts/**"
      - "evals/**"

jobs:
  smoke-tests:
    name: Smoke Tests (rapides)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install deepeval anthropic
      - name: Run smoke tests
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: deepeval test run evals/test_agent_smoke.py

  full-eval:
    name: Full Evaluation
    needs: smoke-tests   # seulement si les smoke tests passent
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install ragas anthropic datasets pandas
      - name: Run full evaluation
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: pytest evals/test_agent_full.py -v

      - name: Upload eval results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: eval-results
          path: evals/results/

Versionner le dataset de test et la baseline

:::callout-insight Le dataset de test doit être versionné dans git comme du code

Si le dataset change sans que le code change, les métriques peuvent "s'améliorer" artificiellement. Si le code change mais le dataset devient obsolète, on passe à côté de nouvelles classes d'erreurs. Traiter le dataset de test comme du code : revue de PR, changelog, pas de modification sans justification. :::

# Script de mise à jour de baseline — à lancer manuellement après validation humaine
# scripts/update_baseline.py

import json
from evals.test_agent_full import run_full_eval

if __name__ == "__main__":
    print("Calcul des nouvelles métriques de baseline...")
    results = run_full_eval()

    with open("evals/baseline.json", "w") as f:
        json.dump(results, f, indent=2)

    print("Baseline mise à jour :")
    for metric, value in results.items():
        print(f"  {metric}: {value:.3f}")
    print("\nN'oubliez pas de commiter baseline.json et de documenter les changements.")

Combien ça coûte en tokens ?

Un pipeline d'évaluation en CI a un coût en tokens à chaque exécution (les métriques Ragas et DeepEval utilisent des LLM en interne).

{ } Code
Smoke tests (10 cas × 2 métriques) ≈ 5 000 tokens → ~0,03 € (Claude Haiku)
Full eval (100 cas × 3 métriques)  ≈ 80 000 tokens → ~0,40 € (Claude Haiku)

Recommandation :
- Smoke tests : utiliser Claude Haiku (suffisant pour les vérifications rapides)
- Full eval : utiliser Claude Haiku ou Sonnet selon la précision requise
- LLM-as-judge final : utiliser Claude Opus (meilleure corrélation avec humains)

# Configurer le modèle utilisé pour les métriques DeepEval
from deepeval.models import DeepEvalBaseLLM
import anthropic

class HaikuJudge(DeepEvalBaseLLM):
    def load_model(self):
        return anthropic.Anthropic()

    def generate(self, prompt: str) -> str:
        client = self.load_model()
        response = client.messages.create(
            model="claude-haiku-4-5-20251001",  # moins cher pour les évals en CI
            max_tokens=500,
            messages=[{"role": "user", "content": prompt}]
        )
        return response.content[0].text

    async def a_generate(self, prompt: str) -> str:
        return self.generate(prompt)

    def get_model_name(self) -> str:
        return "claude-haiku-4-5"

# Utiliser dans les métriques
from deepeval.metrics import AnswerRelevancyMetric
metric = AnswerRelevancyMetric(model=HaikuJudge(), threshold=0.7)

Quand utiliser un pipeline d'évaluation en CI

  • Dès qu'un agent est en production et qu'il existe un historique de cas connus
  • Dès qu'on modifie un prompt — même une virgule peut changer le comportement
  • Quand plusieurs personnes travaillent sur le même agent — pour éviter les régressions croisées
  • Avant tout changement de modèle (migration GPT-4 → Claude, Claude Sonnet → Haiku...)

Quand c'est prématuré

  • En phase d'exploration rapide (prototypes, POC < 2 semaines) — le dataset de test n'est pas stable
  • Quand les cas de test représentatifs ne sont pas encore définis — évaluer avant d'avoir des cas clairs produit des métriques sans sens
Flashcards

Qu'est-ce qu'un pipeline d'évaluation en CI/CD pour un agent LLM ?

Voir la réponse
Réponse

Des tests automatisés qui s'exécutent à chaque modification (prompt, modèle, code) et bloquent le déploiement si les métriques chutent en dessous d'un seuil. Équivalent des tests unitaires pour les agents.

Quelle est la différence entre les smoke tests et la full evaluation ?

Voir la réponse
Réponse

Les smoke tests vérifient 5-10 cas critiques en 2 minutes (détecter une régression majeure). La full evaluation évalue l'intégralité du dataset (50-100 cas) avec toutes les métriques — plus lente et plus coûteuse.

Pourquoi faut-il versionner le dataset de test dans git ?

Voir la réponse
Réponse

Pour que les métriques restent comparables entre versions. Si le dataset change sans traçabilité, une "amélioration" des métriques peut être artificielle (cas plus faciles) plutôt que réelle.

Comment réduire le coût en tokens d'un pipeline d'évaluation en CI ?

Voir la réponse
Réponse

Utiliser Claude Haiku pour les métriques de CI (smoke tests et full eval). Réserver Claude Opus uniquement pour les LLM-as-judge finaux où la corrélation avec les jugements humains doit être maximale.

Qu'est-ce qu'une baseline dans un pipeline d'évaluation ?

Voir la réponse
Réponse

Les métriques de la version précédente, stockées dans un fichier. Elles servent à détecter une régression : si la version actuelle est plus de X points en dessous, le déploiement est bloqué.

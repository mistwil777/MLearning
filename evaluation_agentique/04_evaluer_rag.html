Évaluer un pipeline RAG — Du retriever à la réponse finale

Programme7 jours3-4h/jour

Définition

Un pipeline RAG (Retrieval-Augmented Generation) enchaîne deux étapes distinctes : un retriever qui cherche des documents pertinents dans une base, et un LLM qui génère une réponse à partir de ces documents. Évaluer un pipeline RAG signifie mesurer les deux étapes séparément, car une erreur peut venir de l'une ou de l'autre — et le diagnostic change selon la source.

:::callout-insight Essentiels : - Un pipeline RAG a deux couches d'erreur indépendantes : le retriever et le LLM. - Évaluer séparément les deux est la condition minimale pour diagnostiquer correctement. - Une "mauvaise réponse" peut venir de l'une ou l'autre couche — sans mesure, le diagnostic est impossible. :::

:::situation Leroy Merlin, équipe IA — Chatbot conseil bricolage

L'agent répond aux questions clients sur les produits, techniques de pose, compatibilités. Deux semaines après le lancement, les équipes support remontent que "l'agent donne parfois de mauvaises réponses". Sans évaluation structurée, impossible de savoir si le problème vient du retriever (mauvais documents récupérés) ou du LLM (mauvaise interprétation de bons documents). Le diagnostic prend 3 jours au lieu de 30 minutes avec un framework d'évaluation. :::

La pipeline d'erreur — où ça peut casser

{ } Code
Question utilisateur
       ↓
  [RETRIEVER]  ← peut rater les bons chunks (context recall faible)
       ↓           ou ramener du bruit (context precision faible)
  Chunks récupérés
       ↓
  [LLM]       ← peut halluciner (faithfulness faible)
       ↓           ou répondre hors sujet (answer relevancy faible)
  Réponse finale

:::callout-insight L'erreur la plus courante : blâmer le LLM quand c'est le retriever

Dans 60 % des cas de "mauvaise réponse" RAG, le problème est dans le retriever — les bons documents n'ont pas été récupérés. Le LLM ne peut pas inventer une information qu'il n'a pas. Toujours diagnostiquer le retriever en premier. :::

:::callout-insight Essentiels : - Le retriever échoue en deux modes : bruit excessif (precision faible) ou document manqué (recall faible). - Context precision et context recall sont des métriques complémentaires, pas interchangeables. - Diagnostiquer le retriever en premier avant d'ajuster le prompt ou le LLM. :::

Évaluer le retriever — indépendamment du LLM

Métrique 1 — Hit Rate (taux de couverture)

La question : est-ce que le chunk qui contient la réponse est dans les k premiers résultats ?

def hit_rate_at_k(retriever, test_cases: list, k: int = 5) -> float:
    """
    test_cases : liste de {"question": ..., "relevant_chunk_id": ...}
    Retourne la proportion de questions où le bon chunk est dans le top-k.
    """
    hits = 0
    for case in test_cases:
        retrieved = retriever.search(case["question"], top_k=k)
        retrieved_ids = [chunk.id for chunk in retrieved]
        if case["relevant_chunk_id"] in retrieved_ids:
            hits += 1
    return hits / len(test_cases)

# Exemple
hit_5 = hit_rate_at_k(my_retriever, test_cases, k=5)
print(f"Hit rate @5 : {hit_5:.1%}")
# Si < 0.7 : le retriever rate trop souvent le bon document

Métrique 2 — MRR (Mean Reciprocal Rank)

Le hit rate ne distingue pas "le bon chunk est en position 1" de "le bon chunk est en position 5". Le MRR pénalise les positions basses.

def mrr(retriever, test_cases: list, k: int = 10) -> float:
    """
    Mean Reciprocal Rank : moyenne de 1/rang du premier document pertinent.
    Score parfait = 1.0 (le bon doc est toujours en position 1).
    """
    reciprocal_ranks = []
    for case in test_cases:
        retrieved = retriever.search(case["question"], top_k=k)
        retrieved_ids = [chunk.id for chunk in retrieved]
        try:
            rank = retrieved_ids.index(case["relevant_chunk_id"]) + 1  # 1-indexé
            reciprocal_ranks.append(1.0 / rank)
        except ValueError:
            reciprocal_ranks.append(0.0)  # pas trouvé dans le top-k
    return sum(reciprocal_ranks) / len(reciprocal_ranks)

Métrique 3 — NDCG (pertinence graduée)

Quand plusieurs chunks sont pertinents avec des degrés de pertinence différents.

from sklearn.metrics import ndcg_score
import numpy as np

# Si vos cas de test ont des scores de pertinence (0 = non pertinent, 1 = partiel, 2 = parfait)
true_relevances = [[2, 1, 0, 0, 0]]  # pertinences vraies
predicted_scores = [[0.95, 0.82, 0.71, 0.68, 0.45]]  # scores du retriever

ndcg = ndcg_score(true_relevances, predicted_scores, k=5)
print(f"NDCG@5 : {ndcg:.3f}")

:::callout-insight Essentiels : - Hit Rate @k mesure si le bon document est présent dans les résultats ; MRR mesure s'il est bien classé. - NDCG s'utilise quand plusieurs documents ont des niveaux de pertinence différents (0, 1, 2). - Hit Rate @5 < 0.7 : le retriever rate plus de 30 % des cas — à corriger en priorité. :::

Pipeline d'évaluation complète — bout en bout

import anthropic
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall
from datasets import Dataset
from typing import List

client = anthropic.Anthropic()

def run_rag_pipeline(question: str, retriever, k: int = 5) -> dict:
    """Exécute le pipeline RAG et retourne tous les éléments pour l'évaluation."""
    # Étape 1 : retrieval
    chunks = retriever.search(question, top_k=k)
    context_texts = [chunk.text for chunk in chunks]

    # Étape 2 : génération
    context_str = "\n\n".join(context_texts)
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=500,
        messages=[{
            "role": "user",
            "content": f"Contexte :\n{context_str}\n\nQuestion : {question}\n\nRéponse :"
        }]
    )

    return {
        "question": question,
        "answer": response.content[0].text,
        "contexts": context_texts,
    }


def evaluate_rag_pipeline(test_cases: list, retriever, ground_truths: list = None) -> dict:
    """
    Évalue le pipeline RAG complet sur un dataset de test.
    ground_truths : optionnel — améliore context_recall si fourni.
    """
    results = []
    for case in test_cases:
        result = run_rag_pipeline(case["question"], retriever)
        results.append(result)

    dataset_dict = {
        "question": [r["question"] for r in results],
        "answer": [r["answer"] for r in results],
        "contexts": [r["contexts"] for r in results],
    }
    if ground_truths:
        dataset_dict["ground_truth"] = ground_truths

    metrics = [faithfulness, answer_relevancy, context_precision]
    if ground_truths:
        metrics.append(context_recall)

    scores = evaluate(Dataset.from_dict(dataset_dict), metrics=metrics)

    # Diagnostic automatique
    print("\n=== Diagnostic RAG ===")
    if scores["context_precision"] < 0.7:
        print("⚠ Context precision faible → le retriever ramène trop de bruit (chunks non pertinents)")
    if "context_recall" in scores and scores["context_recall"] < 0.7:
        print("⚠ Context recall faible → le retriever rate des chunks importants")
    if scores["faithfulness"] < 0.8:
        print("⚠ Faithfulness faible → le LLM hallucine par rapport aux documents récupérés")
    if scores["answer_relevancy"] < 0.7:
        print("⚠ Answer relevancy faible → le LLM répond hors sujet ou sur-explique")

    return scores

:::callout-insight Essentiels : - Le diagnostic automatique compare chaque score à un seuil fixe pour orienter l'action corrective. - ground_truth est optionnel mais débloque la métrique context_recall — fournir si possible. - Context precision et context recall sont deux signaux complémentaires sur la qualité du retriever. :::

Construire le dataset de test — la partie la plus difficile

Un bon dataset de test RAG nécessite :

  1. Des questions représentatives de la vraie distribution (pas seulement les cas faciles)
  2. Les chunks pertinents connus pour chaque question (ground truth retrieval)
  3. Une réponse de référence si possible (pour context recall)

Générer automatiquement des questions depuis les documents (TestsetGenerator Ragas)

from ragas.testset.generator import TestsetGenerator
from ragas.testset.evolutions import simple, reasoning, multi_context
from langchain_community.document_loaders import DirectoryLoader
import anthropic

# Charger vos documents
loader = DirectoryLoader("./documents/", glob="**/*.txt")
documents = loader.load()

# Ragas génère des questions + ground truth depuis vos docs
# (nécessite un LLM — ici Claude via LangChain)
from langchain_anthropic import ChatAnthropic
generator_llm = ChatAnthropic(model="claude-opus-5")
critic_llm = ChatAnthropic(model="claude-opus-5")

generator = TestsetGenerator.from_langchain(
    generator_llm=generator_llm,
    critic_llm=critic_llm,
)

testset = generator.generate_with_langchain_docs(
    documents,
    test_size=50,
    distributions={
        simple: 0.5,       # questions directes
        reasoning: 0.3,    # questions qui nécessitent un raisonnement
        multi_context: 0.2 # questions qui nécessitent plusieurs chunks
    }
)

# testset contient : question, ground_truth, contexts, evolution_type
df = testset.to_pandas()
df.to_csv("rag_testset.csv", index=False)

:::callout-insight Générer le testset avec un LLM — est-ce fiable ?

Oui, avec une précaution : vérifier manuellement ~10 % des questions générées. Les LLM tendent à générer des questions "faciles" (réponse directement dans un seul chunk). Augmenter la proportion multi_context et reasoning pour avoir un dataset plus difficile et plus représentatif. :::

:::callout-insight Essentiels : - Un bon testset nécessite des questions variées en difficulté — pas seulement des cas directs. - Augmenter multi_context et reasoning produit un dataset plus représentatif de la vraie distribution. :::

Interpréter les scores Ragas — tableau de référence

Scores Interprétation Action
Faithfulness < 0.7 Hallucinations fréquentes Modifier le prompt système — ajouter "réponds uniquement avec les informations fournies"
Context Precision < 0.6 Retriever trop bruité Réduire k, augmenter le seuil de score minimum, améliorer le chunking
Context Recall < 0.7 Retriever trop étroit Augmenter k, revoir la stratégie de chunking (chunks trop grands ?), reindexer
Answer Relevancy < 0.7 LLM hors sujet Prompt trop large, reformuler la question transmise au LLM
Tout > 0.85 Pipeline sain Surveiller en production — les scores peuvent dériver avec de nouvelles données

:::callout-insight Essentiels : - Chaque métrique cible une couche précise : faithfulness et answer_relevancy → LLM ; precision et recall → retriever. - Tout > 0.85 ne dispense pas d'une surveillance en production — les scores dérivent avec les données. :::

Quand utiliser cette évaluation

  • Avant tout déploiement d'un pipeline RAG en production
  • Après chaque modification du retriever (chunking, embedding model, k)
  • Après chaque modification du prompt LLM
  • Sur une base régulière en production pour détecter la dérive des données

Quand les limites s'appliquent

  • Quand les documents changent fréquemment : le testset devient obsolète et doit être régénéré
  • Quand les questions sont très longues ou multi-tours : Ragas est optimisé pour les échanges en un seul tour
  • Les métriques Ragas utilisent elles-mêmes un LLM en interne — elles ne sont pas gratuites en tokens ni infaillibles

:::callout-insight Essentiels : - Évaluer systématiquement avant tout déploiement ET après chaque modification du retriever ou du prompt. - Les métriques Ragas ont un coût en tokens et ne sont pas infaillibles — vérifier manuellement les cas limites. :::

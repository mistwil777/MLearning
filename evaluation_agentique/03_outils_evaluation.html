Outils d'évaluation agentique — Ne pas tout reconstruire

Programme7 jours3-4h/jour

Définition

Les frameworks d'évaluation agentique sont des bibliothèques et plateformes qui implémentent les métriques, les patterns de test, les tableaux de bord et le traçage d'exécution pour les systèmes LLM et agents. Ils remplacent une infrastructure que la plupart des équipes construisent manuellement — et mal — à chaque projet.

:::situation Startup française (anonymisée), 2024 — Pipeline RAG pour support client

L'équipe a passé 6 semaines à construire un système d'évaluation maison : boucle de test, calcul des métriques, stockage des résultats, dashboard Streamlit. Résultat : fragile, non maintenu, personne ne comprend comment l'interprêter à part la personne qui l'a construit. Découverte tardive de Ragas et DeepEval : ces outils auraient couvert 80 % du besoin en une journée d'intégration. :::

La carte des outils — qui fait quoi

Ragas — Évaluation RAG sans annotation humaine

Ragas (Retrieval Augmented Generation Assessment) est le standard de facto pour évaluer les pipelines RAG. Il calcule 4 métriques principales en utilisant un LLM-as-judge interne.

pip install ragas

Les 4 métriques Ragas

Métrique Ce qu'elle mesure Ce qui peut la faire chuter
Faithfulness La réponse est-elle fidèle aux documents récupérés ? Hallucination — l'agent invente quelque chose absent des chunks
Answer Relevancy La réponse répond-elle à la question posée ? Réponse correcte mais hors sujet
Context Precision Les chunks récupérés sont-ils pertinents ? Retrieval trop large, bruit dans le contexte
Context Recall Les chunks nécessaires ont-ils été récupérés ? Retrieval trop étroit, info manquante 
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall
from datasets import Dataset

# Structure attendue par Ragas
data = {
    "question": [
        "Quelle est la politique de remboursement pour les articles défectueux ?",
        "Quel est le délai de livraison standard ?"
    ],
    "answer": [
        # Réponses générées par votre agent
        "Les articles défectueux sont remboursés sous 30 jours sur présentation de la facture.",
        "Le délai standard est de 5 à 7 jours ouvrés."
    ],
    "contexts": [
        # Chunks récupérés par votre retriever pour chaque question
        ["Notre politique de retour : tout article défectueux remboursé 30 jours après achat avec facture."],
        ["Livraison standard : 5-7 jours ouvrés. Express disponible sous 24h."]
    ],
    "ground_truth": [
        # Réponse de référence (si disponible — optionnel pour certaines métriques)
        "Remboursement sous 30 jours avec facture.",
        "5 à 7 jours ouvrés."
    ]
}

dataset = Dataset.from_dict(data)
results = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall]
)

print(results)
# {'faithfulness': 0.95, 'answer_relevancy': 0.89, 'context_precision': 0.82, 'context_recall': 0.78}

Interpréter les résultats Ragas

{ } Code
faithfulness faible (< 0.8)   → votre LLM hallucine par rapport aux documents
answer_relevancy faible        → votre agent dévie du sujet ou sur-explique
context_precision faible       → votre retriever ramène trop de bruit
context_recall faible          → votre retriever rate des chunks importants

DeepEval — Tests unitaires pour LLM

DeepEval adopte le paradigme pytest : chaque test vérifie un comportement attendu, et le test échoue s'il n'est pas respecté. Ça s'intègre directement dans une CI.

pip install deepeval

import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import (
    AnswerRelevancyMetric,
    FaithfulnessMetric,
    HallucinationMetric,
    ToxicityMetric,
    GEval,
)

# Test 1 — Vérifier qu'une réponse est pertinente
def test_customer_support_relevance():
    test_case = LLMTestCase(
        input="Comment puis-je annuler ma commande ?",
        actual_output=my_agent.run("Comment puis-je annuler ma commande ?"),
        expected_output="Vous pouvez annuler depuis votre espace client sous 24h."
    )
    metric = AnswerRelevancyMetric(threshold=0.7)
    assert_test(test_case, [metric])


# Test 2 — Vérifier qu'il n'y a pas d'hallucination
def test_no_hallucination():
    test_case = LLMTestCase(
        input="Quel est notre délai de retour ?",
        actual_output=my_agent.run("Quel est notre délai de retour ?"),
        context=["Notre politique : retours acceptés sous 14 jours."]
    )
    metric = HallucinationMetric(threshold=0.2)  # max 20% de contenu non ancré
    assert_test(test_case, [metric])


# Test 3 — Critère métier personnalisé avec G-Eval
def test_formal_tone():
    test_case = LLMTestCase(
        input="Bonjour j'ai un problème",
        actual_output=my_agent.run("Bonjour j'ai un problème"),
    )
    metric = GEval(
        name="Ton professionnel",
        criteria="La réponse utilise un ton formel et professionnel, sans familiarités.",
        evaluation_params=["actual_output"],
        threshold=0.8
    )
    assert_test(test_case, [metric])

# Lancer comme des tests pytest normaux
deepeval test run test_agent.py

# Dans la CI (GitHub Actions par exemple)
# - name: Run LLM evals
#   run: deepeval test run tests/test_agent.py

Arize Phoenix — Observabilité locale et gratuite

Phoenix est un outil d'observabilité open source qui tourne localement (pas de données envoyées en dehors). Il intercepte les appels LLM via OpenTelemetry et les affiche dans une interface web.

pip install arize-phoenix openinference-instrumentation-anthropic

import phoenix as px
from openinference.instrumentation.anthropic import AnthropicInstrumentor

# Démarre l'interface web sur http://localhost:6006
session = px.launch_app()

# Instrumente automatiquement tous les appels Anthropic
AnthropicInstrumentor().instrument()

# Vos appels normaux sont maintenant tracés
import anthropic
client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=1000,
    messages=[{"role": "user", "content": "Résume ce document : ..."}]
)

# → Phoenix capture : prompt, réponse, tokens, latence, coût estimé
# → Visualisable sur http://localhost:6006

:::callout-insight Pourquoi Phoenix plutôt que LangSmith si on débute ?

LangSmith est excellent mais SaaS — vos données de prod passent chez LangChain. Phoenix tourne localement, zéro configuration de compte, idéal pour du développement ou des contextes où les données sont sensibles. Pour un projet client Capgemini, Phoenix est souvent le choix par défaut. :::

Promptfoo — Tester les prompts comme du code

Promptfoo est un outil CLI qui permet de définir des suites de tests pour vos prompts et de les exécuter en CI. Il supporte plusieurs providers (Anthropic, OpenAI, Mistral...) et permet la comparaison A/B de prompts.

# promptfooconfig.yaml
prompts:
  - "Tu es un assistant support client. Réponds à : {{question}}"
  - "Tu es un expert service client FNAC. Sois concis. Question : {{question}}"

providers:
  - anthropic:claude-opus-5
  - anthropic:claude-haiku-4-5-20251001  # comparaison coût/qualité

tests:
  - vars:
      question: "Comment annuler une commande ?"
    assert:
      - type: contains
        value: "espace client"
      - type: llm-rubric
        value: "La réponse explique clairement comment annuler sans être agressive"

  - vars:
      question: "Je veux un remboursement"
    assert:
      - type: not-contains
        value: "impossible"  # jamais dire "impossible" au client
      - type: llm-rubric
        value: "La réponse propose une solution ou un chemin vers une solution"

npx promptfoo eval
# Tableau comparatif des deux prompts × deux modèles
# Score de réussite, coût estimé, latence

Helicone — Proxy transparent pour logger tous les appels

Helicone s'insère entre votre code et l'API Anthropic/OpenAI sans modifier votre code existant. Un seul changement d'URL pour avoir : logs, coûts, latences, rate limits.

# Avant (appel direct)
client = anthropic.Anthropic(api_key="sk-ant-...")

# Après (via Helicone) — une seule ligne change
client = anthropic.Anthropic(
    api_key="sk-ant-...",
    base_url="https://anthropic.helicone.ai",
    default_headers={"Helicone-Auth": "Bearer sk-helicone-..."}
)

# Tout le reste de votre code est identique
# Helicone capture : modèle, prompt, réponse, tokens, coût, latence, user_id

Plan gratuit : 10 000 requêtes/mois — suffisant pour le développement et les projets académiques.

Quand utiliser ces outils

  • Dès le début d'un projet LLM/agent — pas après que les problèmes apparaissent
  • Avant de modifier un prompt ou de changer de modèle : établir une baseline avec DeepEval ou Ragas
  • Pour un pipeline RAG : Ragas est non-négociable — sans lui, vous optimisez à l'aveugle
  • Pour les coûts : Helicone ou Weave dès qu'on passe à un usage régulier

Quand ne pas les utiliser

  • Ragas sans contexte fourni : les métriques context_* nécessitent que les chunks récupérés soient accessibles — si votre retriever est une boîte noire, l'intégration est plus complexe
  • DeepEval pour des tâches créatives où le critère de succès est intrinsèquement subjectif — les métriques seront basses même sur de bonnes réponses
  • Helicone si les données de vos appels LLM sont confidentielles (contrats, données médicales) — envisager Phoenix local à la place
Flashcards

Quelles sont les 4 métriques principales de Ragas ?

Voir la réponse
Réponse

Faithfulness (pas d'hallucination), Answer Relevancy (réponse pertinente à la question), Context Precision (chunks récupérés pertinents), Context Recall (chunks nécessaires récupérés).

Quelle est la différence entre DeepEval et Ragas ?

Voir la réponse
Réponse

Ragas est spécialisé RAG avec des métriques prédéfinies. DeepEval est un framework généraliste qui permet d'écrire des tests unitaires style pytest pour n'importe quel agent ou LLM, avec des métriques personnalisables.

Pourquoi utiliser Arize Phoenix plutôt que LangSmith dans un projet client ?

Voir la réponse
Réponse

Phoenix est open source et local — aucune donnée n'est envoyée en dehors. LangSmith est SaaS, ce qui peut poser des problèmes de confidentialité sur des projets avec données sensibles.

Qu'est-ce que Promptfoo et dans quel contexte l'utiliser ?

Voir la réponse
Réponse

Un outil CLI pour tester et comparer des prompts en CI/CD. Permet de détecter automatiquement une régression de prompt avant un déploiement, et de comparer plusieurs modèles sur les mêmes cas de test.

Si faithfulness est faible dans Ragas, quel est le problème ?

Voir la réponse
Réponse

Le LLM hallucine — il affirme des choses absentes ou contredites par les documents récupérés. Le problème est dans le LLM ou son prompt, pas dans le retriever.
